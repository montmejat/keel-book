Start herekeel · drydock

Welcome

Two projects that meet on a CAN bus. keel is a robot's software. drydock is the robot's motors, simulated, behind the same bus the real ones would be on.

keel is a robotics middleware in about 10,000 lines of Rust: processes exchanging messages through shared memory, a daemon per machine, real-time loops, tracing, recording, deployment, and a control layer that drives motors. drydock plays a robot's motors on a virtual CAN interface (vcan0), answering frame for frame and as fast as a real bus carries frames, while MuJoCo moves the robot's body behind them.

The software that drives drydock is the software that drives the robot. Swap vcan0 for can0 and keel is talking to real motors; nothing else changes. That's the point of drawing the line at the bus: the driver, its timing and its handling of every answer run for real, and only the hardware is simulated.

The one-paragraph model. A keel dataflow is a set of processes (nodes) wired by name. A controller node gets the joints' state and answers with a command for each. A bus-master node, keel-can, turns commands into CAN frames and the motors' answers into the next state. drydock sits at the other end of the bus: it decodes the frames, runs each motor's firmware, pushes on the joints of a MuJoCo model, and answers.

OpenArm in ten minutes

From two clones to keel driving a simulated OpenArm over CAN FD, its first joint swinging and its gripper opening and closing.

OpenArm is an open-source arm on Damiao motors: seven joints and a gripper, eight motors on one CAN bus. drydock loads Enactic's own MuJoCo model of it; keel drives it as it would the real one.

What you need

  • Linux (x86-64), Rust (stable), a C compiler, git, curl (on Debian or Ubuntu: sudo apt install build-essential git curl).
  • sudo, once per boot, to make the virtual CAN interface. Everything else runs as you.
  • Both repositories side by side:
git clone https://github.com/montmejat/keel
git clone https://github.com/montmejat/drydock

3. keel, driving it

# in keel/
cargo build
./target/debug/keel doctor examples/openarm.yml   # what's missing, with the command to fix it
./target/debug/keel run examples/openarm.yml

Start the two in either order: keel-can waits for the motors to answer, saying so in keel logs arm.

In another terminal, look:

./target/debug/keel logs arm          # each motor: MIT mode, its ranges, read from its registers
./target/debug/keel logs controller   # "3.0s joints at -0.40 -0.00 -0.00 +1.64 -0.00 -0.00 +0.06 -1.03 rad"
./target/debug/keel trace             # state → command: ~15–40 µs end to end
./target/debug/keel top               # live: nodes, links, latencies, logs
./target/debug/keel stop              # or Ctrl-C in the first terminal: the motors are disabled

Joint 1 swings ±0.4 rad every four seconds, joint 4 holds its bend at 1.64 rad (against gravity, with OpenArm's own gains), and the gripper motor goes between 0 and −1.03 rad every two seconds.

Try breaking it. Stop drydock and start it again with --break openarm_joint4:dead@5: five seconds in, the elbow's motor gives no torque. In keel logs controller, joint 4 drops to its stop at 2.44 rad. Nothing else reports it; see Encoders and faults.

The one place they touch

The CAN bus, and the frame format of Damiao's motors on it. keel has its own copy of that format (keel_control::damiao); drydock has its own (damiao::protocol). Neither depends on the other: keel must stay free of a simulator and of C libraries, and drydock answers any bus master, not only keel (OpenArm's own C++ library drives it just as well). The wire between them draws the contract.

keelruntime

Dataflows and nodes

A dataflow is a YAML file of processes wired by name. keel starts them, moves their messages through shared memory, and stops them in order.

Processes and planes

On one machine, keel run is the coordinator and the only daemon, in one process. The daemon spawns nodes but stays off the data path: descriptors go node to node through rings in /dev/shm, woken by futexes.

Two planes, kept apart on purpose. The data plane moves messages, and must be fast: about 5.6 µs for a round trip between two nodes, 5 million messages a second, whatever the payload's size, since only a descriptor moves. The control plane starts, stops and reports; every tool (keel top, keel web, an agent's MCP server) is a client of it, and never touches a payload.

A dataflow file

nodes:
  - id: arm
    path: ../target/debug/keel-can          # or `build: <binary>`: keel builds and ships it
    args: ["--interface", "vcan0", "--protocol", "damiao", "--fd", "true", "--hz", "500",
           "--motors", "0x01:0x11,0x02:0x12,…"]
    restart: on-failure
    inputs:
      command: { source: controller/command, keep: latest }

  - id: controller
    path: ../target/debug/openarm-wave
    rt: { priority: 80, cpus: [3] }         # SCHED_FIFO 80, pinned: needs an rtprio limit
    inputs:
      state: { source: arm/state, keep: latest }   # <input>: <node>/<output>
FieldMeans
inputsname: node/output, or with keep: all (every message, the sender waits for a slow receiver) or latest (only the newest, the sender never waits: controllers, recorders, viewers)
rtSCHED_FIFO priority and CPUs; any rt: also locks memory and sets a 1 ns timer slack
phase_uswhere in their period the node's periodic loops tick
restart, watchdog_msnever, on-failure, always; kill a node that stops taking or sending
machines, machinea dataflow across machines: a daemon address per name, a name per node

A node

use keel::{Event, Node};

fn main() -> std::io::Result<()> {
    let mut node = Node::from_env()?;              // the daemon told it who it is
    while let Event::Input { id, data } = node.next_event()? {
        // `data` is the payload, in shared memory; `data.stamp_ns()` the moment it describes
        node.send_output("out", &data)?;
    }
    Ok(())                                         // Event::Stop: upstream is done
}

Payloads are raw bytes to keel; layouts belong to the crates above it (keel-control gives joints' states and commands one). The daemon starts nodes only once all have registered, stops them from the sources down, and sends SIGTERM, then SIGKILL, to those that don't listen.

Latency is from a message's publishing to its being taken; processing, from taken to released. A trace follows one message through everything it caused, across machines too: here a state, the command it caused, and the command reaching the bus master, 23.5 µs in all.

Stamps, recordings and replays

Every message carries a stamp: the moment of the world it describes, not when it was sent. A joints' state is stamped with when the joints were read; a command inherits its state's stamp. Controllers take their time from stamps, never from the clock, which is what lets one run unchanged against a robot, a simulation in lockstep, or a replay at twice the speed.

keel run examples/pipeline-recorded.yml                 # a recorder node writes its inputs
keel replay <file> examples/pipeline.yml --speed 2      # sources replaced by the recording
keel export <file> dataset/ --channel brightness         # files and an index.csv

A recorder with --last 2.5 is a flight recorder: it keeps the last seconds in memory, and the daemon saves them when a node fails, as a recording that replays the failure.

keelkeel-control

The control layer

Joints and controllers as ordinary nodes. Hardware is whatever publishes state and takes command; the dataflow file is the hardware interface.

keel-control is a crate above the node API, built with only what any keel user gets. It gives two payloads a layout, one entry per joint, back to back, little-endian:

MessagePer jointBytes
Stateposition (rad), velocity (rad/s), effort (N m: the torque the drive gives), f64; its status: flags (drive error, disabled, underpowered, behind, frozen) and the drive's own code, u3232
Commandposition (rad), velocity (rad/s), kp (N m/rad), kd (N m s/rad), effort (N m), f6440

A command is an MIT command

A command asks for the torque kp (position − θ) + kd (velocity − θ̇) + effort, where θ and θ̇ are the joint's as it is: a virtual spring and damper toward a target, plus a feed-forward torque. It's the command format of quasi-direct-drive motors, called MIT mode after MIT's Mini Cheetah. One format covers every kind of control: a plain torque (kp = kd = 0, Command::effort(τ)), stiff position control (high kp), compliance (low kp), model-based control (a target plus gravity compensation in effort).

Whoever drives the joint closes that loop, and the controller doesn't know who: a Damiao motor in its firmware, tens of thousands of times a second; keel-sim every simulation step; keel-can once a cycle, for drives that only take a torque. (Decision 0031.)

A cycle

A bus master or simulation ticks once a period: it publishes the state, waits up to a deadline for the command that answers it, and acts on it in the same cycle.

--cycleThe command actsFor
same (default)as soon as it comes, if before --deadline-us (300 µs); else at the next tick, the previous one meanwhilecontrollers that answer fast: ~20 µs from state to command at 1 kHz
nextat the next tick: a constant one-period delaycontrollers that can't answer within the deadline
lockstepwhen it comes; no clock, no deadlinesimulations only: as fast as the controller goes

The answer is recognised by its trace: a controller that sends while holding the state names the state as its parent. Late commands are counted, and logged once a second: 3 of 500 commands missed the 300µs deadline.

Time

  • Stamps: a controller's dt is the gap between two states' stamps.
  • Phases: periodic loops tick on multiples of their period on the machine's clock, so loops of one period tick together whenever they started; phase_us moves one along its period.
  • Waiting: a node sleeps on a futex (~5 µs a hop), spins (~0.5 µs, a whole core), or spins only around when its inputs are due (~1 µs, a few percent of a core).

In full: docs/control.md; decisions 0021, 0027, 0028, 0029.

Joints and drivers

A driver is what its joints need: count, start, read, write, stop. One loop runs any of them.

pub trait Joints {
    fn count(&self) -> usize;
    fn check(&mut self) -> io::Result<()> { Ok(()) }   // for keel doctor: do the drives answer?
    fn start(&mut self) -> io::Result<()> { Ok(()) }   // modes, enable
    /// Every joint's state and the moment it describes, once there's a whole one.
    fn read(&mut self, states: &mut [State]) -> io::Result<Option<u64>>;
    /// This cycle's commands, the newest there are; None before the controller's first.
    fn write(&mut self, commands: Option<&[Command]>, states: &[State]) -> io::Result<()>;
    fn stop(&mut self) -> io::Result<()> { Ok(()) }    // disable
}

JointLoop::new(joints, Settings::from_args()?, &node)?.run(&mut node)

JointLoop is everything else, written once: the tick, publishing the state, waiting for its command within the cycle, one write per cycle (the previous command again when the controller is late), the log lines for late commands and silent joints, and stop however the loop ends. (Decision 0032.)

Three drivers

DriverNodeWhat it does
damiao::DamiaoJointskeel-can --protocol damiaoDamiao's motors in MIT mode; the loop closes on the motors. Below.
can::CanJointskeel-can (default)made-up drives (keel-can-motor's): a torque frame and a state frame per joint; the command's law worked out here once a cycle
plant::Pendulumskeel-simpendulums stepped a period at a time, stamped with the simulation's time; lockstep possible

Damiao's motors, from keel's side

  1. Start: for each motor in --motors (its id and the id it answers on, in joint order), one request at a time: write CTRL_MODE = 1 (MIT) and check the answer says 1; read PMAX, VMAX, TMAX, the ranges values are packed into. A motor that doesn't answer within 100 ms is asked again until it does, with one line in the log ("waiting for motor 0x01 on `vcan0` … is the robot, or drydock, running?"): the robot may be started after keel. Then enable all.
  2. Each cycle: one round, a frame to each motor. The motors speak only when spoken to, and answer each frame with their state; those answers are the next cycle's state, stamped with when their round went out.
  3. Before the first command: the round asks for feedback (0x7FF … CC) without commanding anything.
  4. Errors in a motor's status (overheating, communication lost…) and changes of status go to the log, once each.
  5. Stop: disable all, however the dataflow ended (except SIGKILL).

Why read ranges from the motors? They're per-motor settings, and the published tables disagree: OpenArm's driver packs a DM4340's velocity into ±10 rad/s, Damiao's reference driver into ±8. A table would be wrong for one of them; the motor isn't.

Writing a driver

Another vendor's motors, a serial servo bus, EtherCAT: implement Joints in keel-control, and add two lines to a node's main. The cycle's behaviour, and its fixes, come with JointLoop. Drivers belong in the library, binaries are wiring.

Writing a controller

A node with a state input and a command output, which answers each state while it holds it.

This is examples/openarm/src/main.rs, cut to its loop: OpenArm's home pose with openarm_ros2's gains, the first joint swinging, the gripper working.

let mut node = Node::from_env()?;
let (mut started, mut commands) = (None, Vec::new());
while let Event::Input { data, .. } = node.next_event()? {
    let now = data.stamp_ns();                                  // time from the stamp, never the clock
    let t = (now - *started.get_or_insert(now)) as f64 / 1e9;
    let states: Vec<State> = State::read(&data).collect();
    commands.clear();
    for i in 0..states.len() {
        let (position, velocity) = match i {
            0 => (0.4 * (TAU * 0.25 * t).sin(), 0.4 * TAU * 0.25 * (TAU * 0.25 * t).cos()),
            7 => (if t % 4.0 < 2.0 { 0.0 } else { CLOSED }, 0.0),
            _ => (HOME[i], 0.0),
        };
        commands.push(Command { position, velocity, kp: KP[i], kd: KD[i], effort: 0.0 });
    }
    // Sent while `data` is held: the command answers this state, within its cycle.
    node.send_with("command", commands.len() * Command::LEN, |p| Command::write(&commands, p))?;
}

Three rules

  1. Send while holding the state (or with send_caused_by). A command sent after the state is dropped answers nothing: the joints wait for their deadline every cycle. Such a controller wants --cycle next.
  2. Take time from stamps. Then lockstep, replay and the robot look the same to it.
  3. Know nothing of what's behind the joints. If a controller needs to know, the messages are missing something.

Where the loop closes

With MIT commands, a controller chooses per joint and per cycle: send targets and gains and let the drives close a stiff loop at their own rate, or send kp = kd = 0 with a torque and close the loop itself at the bus's rate. The first is what an arm on CAN wants: the bus carries setpoints at hundreds of hertz, the drive holds them at tens of kilohertz. The second is whole-body control, model-based torque: then the bus's rate is the loop's rate (see bandwidth).

The PID (keel-pid) is the other example: it sends plain torques, closing its loop in keel against keel-sim's pendulums or keel-can-motor.

drydockoverview

What drydock is

A robot's motors on virtual CAN buses, their physics simulated in MuJoCo. A bus master talks to it as it would to the real motors.

Most simulators draw their line above the driver: the robot's software talks to the simulator through an adapter of its own (a Python API, a TCP protocol), and the driver code only ever runs on the robot. drydock draws its line at the bus. Everything above it is the robot's own software, unchanged; drydock is the part a simulator usually leaves out.

What
Realthe bus master and its driver library, its socket calls, its threads and timing on the host, its handling of every answer
Modelledeach motor's firmware (answers, states, registers, timeout, MIT law), its torque limit and transmission, its encoder's errors and its faults, the bus's timing (frame lengths, arbitration), the robot's mechanics (MuJoCo, from the robot's own model)
Absentthe bus's electrical faults (error frames, bus-off), Damiao's other control modes, thermals, power

Using it

drydock <robot.yml> [--lockstep <hz>] [--break <joint>:<fault>]...
  • The robot file names a MuJoCo scene and the buses that drive it: Robot files.
  • In real time (the default), frames take as long as on a real bus; in lockstep, time follows the bus masters' cycles: Time and the bus.
  • Motors break on a flag: Encoders and faults.

A bus

can
the SocketCAN interface. One bus per arm is common; ids are per bus, so two arms may share them.
fd
motors on CAN FD answer in it and understand classic frames too; motors on classic CAN ignore CAN FD frames, with a note (a real bus would carry error frames). The interface must carry CAN FD (MTU 72).
bitrate, data_bitrate
how fast frames cross, in real time.
reply_us
a motor's own delay before answering. Unknown for Damiao's motors, so none by default.

A motor

joint
a hinge or slide joint in the scene. The scene's own actuators on it are silenced (zero gain and bias): the motor drives it now.
model
DM3507, DM4310, DM4310_48V, DM4340, DM4340_48V, DM6006, DM8006, DM8009, DM10010L, DM10010, DMH3510, DMH6215, DMG6220: sets PMAX, VMAX, TMAX to the factory's.
id, master_id
where commands go, where answers come from (11-bit, below 0x7FF).
limits
{ p, v, t }: any of PMAX, VMAX, TMAX that differ from the model's. They're registers; a bus master can read them.
peak_torque
the most torque it gives, N m. TMAX by default, which is only a packing range: a DM-J4310 peaks at 7 N m, not 10.
timeout_ms
without a frame this long, it disables itself with status D (communication lost). Off by default, as from the factory.
transmission
{ ratio, offset }: the joint is at offset + ratio θ when the motor is at θ; a motor torque τ puts τ / ratio on the joint. OpenArm's gripper motor turns, its fingers slide: 0.042 m per rad, as OpenArm's own driver assumes.
encoder, fault
what its encoder gets wrong, and how and when it breaks: Encoders and faults.

The split is the point. The scene is the mechanics (links, masses, rotor inertia as armature, damping, friction), unchanged from whoever published it: OpenArm's comes from Enactic's openarm_mujoco, MuJoCo Menagerie's models work as they are. The motors' behaviour stays out of the scene, where it would have to be faked with MuJoCo actuators.

One protocol, spoken completely: Damiao's motors in MIT mode, frame for frame against Damiao's reference driver and OpenArm's library.

Choices that matter to a driver

  • Every frame to a motor is answered, with the state of the moment it landed, as the real motors do.
  • Unknown registers get no answer. A made-up value would let a driver believe something false; a missing answer is a failure the driver already handles.
  • Refused writes answer with the kept value. Writing another mode to CTRL_MODE answers 1; a driver that checks its writes (both reference drivers do) finds out.
  • Packing is the real packing: 16 bits of position, 12 of velocity, gains and torque, clamped to their ranges. So a 12-bit field has no exact zero: an idle motor reports −0.005 N m on a ±10 N m range, as a real one would.
  • Temperatures are always 25 °C; there's no thermal model.

The frames themselves are drawn in The wire between them and listed in Messages and frames.

drydockclock

Time and the bus

In real time, frames take as long as they would on a real bus. In lockstep, time follows the bus masters.

Real time, with bus timing

A physics step runs each timestep of the wall clock (the scene's <option timestep>, 1 ms for OpenArm). Between steps, frames cross the bus as on a real one:

  1. A frame from the master waits for the bus. When the bus frees, the waiting frame with the lowest id goes first: arbitration. A master's commands (ids 0x01–0x08) go before the motors' answers (0x11–0x18).
  2. It takes as long as its bits, counted as ISO 11898-1 lays them out: the CRC, the stuff bits (one after any five equal bits), CAN FD's data phase at the faster rate.
  3. When it's across, its motor acts on it, and the answer queues in turn.
drydock: vcan0: busy 96% of the last 1.0 s; frames waited up to 0.85 ms for it

A bus kept busy (90% of a second, or a frame waiting a millisecond) says so once a second. That line is OpenArm on classic CAN at 500 Hz: it just fits. Falling more than 100 ms behind the wall clock is said and forgiven, not caught up.

Lockstep

--lockstep <hz>: physics advances 1/hz seconds once every motor, on every bus, has had a frame since the last advance. Answers go out at once, with the state before the advance, so a master sending each motor a command a cycle reads, a cycle later, what its commands did. Runs repeat frame for frame and go as fast as the masters; frames take no time. A master that leaves a motor out of its cycles stalls time.

Why not a clock protocol? CANopen's SYNC would have been one, but Damiao's motors don't speak it, and a master shouldn't have to change to be simulated. "Every motor has heard from its master" needs nothing on the wire.

drydockeffects

Encoders and faults

Real motors read their angle imperfectly, and break. drydock's do too, seeded, so a run that finds a problem repeats.

An encoder

encoder: { delay_ms: 0, bias: 0, drift: 0, noise: 0.0005, quantum: 0.0004 }   # radians; all 0 by default

In the order a reading meets them: a delay (it shows the joint as it was), a bias drawn once, a drift that wanders as a random walk, white noise, and counts (the smallest step it tells apart). The motor's firmware closes its loop on that reading and answers with it: a noisy encoder makes a noisy motor, as on a robot.

A frame's way through, in real time

  1. run reads a frame from a bus's socket and queues it on that bus's timeline.
  2. When it's across (above), dock delivers it; damiao::bus finds whose it is.
  3. The motor reads its angle through its transmission and encoder, acts on the frame, and answers.
  4. The answer queues on the same timeline, ready reply_us later; when it's across, run sends it to the master.

A step's way through

  1. For each motor: its joint's angle and velocity, through its transmission, then its encoder.
  2. Its law asks for a torque (none unless enabled; error D here if past its timeout).
  3. The actuator gives what it can (peak, dead, weak); the motor records it, to report.
  4. Through the transmission, it's the force on the joint (MuJoCo's qfrc_applied). MuJoCo steps once.

Decisions

  • MuJoCo's C library through a C shim: the only code touching MuJoCo's structs is compiled against its headers, so Rust mirrors no struct layout. MuJoCo is linked with an rpath, found at build time in ~/.cache/drydock or MUJOCO_DIR.
  • The C library, not MJX or MuJoCo Warp: one world stepped as the buses ask is a CPU's job. The GPU versions read the same MJCF.
  • The firmware apart from the physics: limits, noise and faults live in the drivetrain, not in the protocol's code. A second protocol (Dynamixel, for serial servos) would be a sibling of damiao on a sibling of can; the rest serves it as it is.

In full: drydock's docs/architecture.md.

Invariants

Togethertiming

One cycle, end to end

From a state published by keel to the next one, through drydock's bus and motors. OpenArm at 500 Hz.

  1. keel-can ticks and publishes the eight joints' state: the previous round's answers, stamped with when that round went out.
  2. openarm-wave answers within ~15–40 µs with eight MIT commands.
  3. keel-can sends them, one round, on vcan0.
  4. drydock carries them across one at a time; each reaches its motor when its last bit has.
  5. Each motor takes its command and answers with position, velocity and torque. The answers cross once the commands have: their ids are higher.
  6. Meanwhile MuJoCo steps every millisecond, each motor pushing on its joint.
  7. At the next tick, the answers are the state.

What the state's stamp means

The state published at a tick is what the motors said as the previous round landed: about one period old, plus the round's time on the bus. Its stamp is when that round went out, the closest moment keel knows to when the motors measured. A fresher state needs a second round within the cycle, at twice the bus load; it's on keel's list.

What to look at

  • 5.3 s: J4's torque drops to zero, and the elbow falls under gravity to its stop, 2.44 rad, in 0.3 s.
  • As it falls, the torque asked grows: the command's law, kp × (target − position) + kd × (velocity asked − velocity), pushes harder the further the joint is from its target. It settles at −52.4 N m, more than a DM4340's 28 N m peak.
  • 5.8 s: after half a second of giving less than 30% of what it's asked, keel-can's loop marks J4 underpowered in its state, and says so in its log with the numbers.
  • 5.9 s: and behind: 0.87 rad from its target for half a second.
  • The other joints carry on. J1 still swings and the gripper still opens and closes. No node stops or slows down.

The flags travel in the state, so the controller, the recorder and a replay all see them. The log says it in words, which is what an agent found through keel-mcp in the agent scenarios (Machines, deployment, agents).

CAN, CAN FD and bandwidth

Why eight motors fit at 1 kHz on CAN FD and not on classic CAN, what sets the limit, and what to do with a longer chain.

A frame's two speeds

An 8-byte Damiao frameClassic, 1 Mbit/sCAN FD, 1 + 5 Mbit/s
Header and tail (id, arbitration, ACK, end)~47 bits, 1 Mbit/s~30 bits, 1 Mbit/s
Data, CRC, stuffing~64–88 bits, 1 Mbit/s~96–113 bits, 5 Mbit/s
One frame111–135 µs~49–57 µs
A cycle of 8 motors (16 frames)1.8–2.2 ms0.8–0.9 ms
Bus load at 500 Hz90–110%~41%
Bus load at 1 kHzdoesn't fit~82%

What sets the limit

CAN has no master. In every bit of a frame's header, every node takes part: two nodes starting at once both watch the wire, and the one sending a 1 that reads back a 0 has lost and stops (arbitration); receivers acknowledge a frame by driving a bit of that same frame. So one bit time must cover the signal's round trip on the cable (about 5 ns per metre each way) and each transceiver's delay (100–250 ns). Bit rate times bus length is about constant:

Nominal rateBus length, roughly
1 Mbit/s~40 m (25 m in practice)
500 kbit/s~100 m
250 kbit/s~250 m

CAN FD's trick: after arbitration one node transmits alone, so its data phase needs no round trip and can go faster, limited by signal quality (2–5 Mbit/s, 8 with newer transceivers). The header can't, and for 8-byte payloads it's about 60% of a frame. The useful bandwidth is small: about 1.2 Mbit/s of payload on CAN FD, 0.5 on classic.

A longer chain

Motors on one CAN FD busBus time per cycleFastest loop
8 (an arm)~0.83 ms~1.2 kHz
15~1.6 ms~640 Hz
30 (a humanoid)~3.1 ms~320 Hz
  • More buses: a bus per limb, on a multi-channel adapter. drydock's robot files take several; keel's controller waiting for every bus's state each cycle is still to do.
  • Fewer frames: some motors take one frame for several (DJI's M3508, four at a time). Damiao's don't.
  • A faster bus: EtherCAT, 100 Mbit/s full duplex, one frame passing through every drive as each reads and writes its part. 100 µs cycles for dozens of axes: what fast industrial arms and many humanoids use.
  • Check the adapter: a full-speed USB-CAN adapter moves data every 1 ms, which caps a round trip before the bus does; high-speed USB, every 125 µs.

Does 1 kHz matter? With MIT commands, the stiff loop runs inside each motor, much faster than the bus; the bus carries setpoints and gains, and a few hundred hertz is plenty for an arm. It matters when the computer closes the loop itself, with pure torques: then the bus's rate is the loop's.

Recipes

Short paths for the things you'll want to do next.

A new robot

  1. Find or write its MJCF. MuJoCo Menagerie has many (I2RT's YAM arm, on DM4340 and DM4310, is in it). Keep it unchanged; drydock silences its actuators on driven joints.
  2. Write a robot file next to it: a bus, and a motor per driven joint, with its model, ids, and any limits, transmission or peak torque.
  3. Run drydock on it, and talk to it first with something simple: drydock's wave example takes any robot file (cargo run --release --example wave -- my/robot.yml), and swings every motor on the first bus.
  4. In keel, a dataflow with keel-can --protocol damiao --motors id:master,… and your controller; copy examples/openarm.yml.

Break a motor, and see what keel sees

# drydock
./target/release/drydock examples/openarm/robot.yml --break openarm_joint4:dead@5

./target/debug/keel logs arm              # "joint 4 (openarm_joint4): gives 0.0 N m of the -52.4 asked; +0.87 rad from its target (1.57)"

Try freeze too: the reported position stops moving, and the motor pushes its full torque against what it thinks is an error. The arm's node says that too: "its position reads 0.160 rad, unchanged for 0.6 s, while its target went to 0.39". And examples/agent/run.sh openarm-dead (-weak, -freeze, -healthy) asks an agent what's wrong, with keel's tools only, and grades its answer.

Repeatable, faster than real time

Run drydock with --lockstep 500: physics advances 2 ms each time every motor has had a frame. keel-can keeps time itself, so the run goes at keel's pace; with a bus master that sends as fast as answers come, it goes as fast as both can. Two lockstep runs give the same frames, noise included (it's seeded).

Classic CAN, to see the limit

Set the bus's fd: false in a copy of OpenArm's robot file, and give keel-can --fd false. At 500 Hz drydock reports the bus 96% busy; at 1 kHz states stop coming whole, and keel-can says so.

On the real arm

sudo ip link set can0 type can bitrate 1000000 dbitrate 5000000 fd on
sudo ip link set can0 up
# or OpenArm's own tool: openarm-can-configure-socketcan can0 -fd

Then, in examples/openarm.yml, --interface can0. Nothing else changes. Before trusting a controller on hardware, run it against drydock with the faults it might meet.

Glossary

arbitration
how CAN picks the next frame: all waiting senders start at once, and the lowest id wins without a collision.
bit stuffing
an extra opposite bit after five equal ones, so the bus never goes long without an edge. Makes a frame's length depend on its content.
BRS
bit rate switch: a CAN FD frame's flag for sending its data at the faster rate.
CAN FD
CAN with frames up to 64 bytes and a faster data phase. Backward compatible: an FD node reads classic frames.
controller
the node that answers each state with a command.
cycle
one period of a joints' loop: state out, command in, one round to the drives.
dataflow
a YAML file of nodes and the wiring of their inputs.
drivetrain
in drydock, what's between a motor's firmware and its joint: actuator, transmission, encoder, faults.
id, master id
a Damiao motor's CAN id, where commands go; and the id its answers go out on.
keep: latest
an input that only ever holds the newest message; its sender never waits.
lockstep
a simulation stepping when its controller answers, not on a clock: repeatable, as fast as both go.
MIT mode
a command of target position, velocity, kp, kd and torque; the drive applies kp·Δp + kd·Δv + τ. After MIT's Mini Cheetah.
MJCF
MuJoCo's model format: bodies, joints, masses, actuators.
node
a process in a dataflow.
phase
where in its period a node's periodic loop ticks.
PMAX, VMAX, TMAX
a Damiao motor's registers: the ranges position, velocity and torque are packed into.
round
keel-can's frames of one cycle: a frame to each motor.
same cycle
acting on a command in the cycle whose state it answers, if it comes before the deadline.
stamp
the moment of the world a message describes, in its header.
transmission
how a motor's turning moves its joint: a ratio and an offset.
vcan0
a virtual CAN interface: frames written to it go to every other socket on it, instantly.

Invariants

  • keel is Rust only, with few dependencies (0010), no C libraries, and doesn't depend on drydock.
  • The dataflow is the hardware interface: controllers never know what's behind the joints. Drivers implement Joints, in the library; binaries are wiring.
  • Controllers take time from stamps.
  • keel and drydock each keep their own copy of Damiao's frame format, tested against the same bytes.
  • drydock answers only what it simulates; an unknown register gets no answer, not a made-up value.
  • drydock's faults say nothing: don't make a broken motor report an error it wouldn't on hardware.

Conventions

  • Writing: plain, short sentences; say what something does, not what it is called; no hype. Docs and comments say why.
  • Decisions: a change of direction in keel gets a record in docs/decisions/, and a row in its README.
  • Formatting: rustfmt.toml in each repository (120 columns). In keel, format only the files you touched: some existing files aren't formatted, and reformatting them muddies a change.
  • Commits: a short subject, a body saying what and why. Ask before committing, pushing or deleting.

Gotchas

  • vcan0 needs root once per boot; some machines refuse unprivileged network namespaces.
  • drydock's tests need MuJoCo; OpenArm's example needs its setup script; neither is in CI.
  • A 12-bit field has no exact zero: compare packed values to a quantum, not to 0.
  • On a bus, a register answer and a feedback frame share the master id: ask for registers only when no commands are in flight.
